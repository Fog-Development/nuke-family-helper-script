# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a userscript for the Nuke Family faction in the online game Torn. The script enhances the game interface with faction management tools including shitlist management, contract tracking, hospital row highlighting, reputation display, and ML recruiting scores. The script integrates with the Nuke.Family API and requires faction leadership permissions for most features.

The legacy "Payout Helper" features (cash payouts on faction controls, xanax payouts on the armoury drugs tab) were removed in the modular refactor — payouts are handled elsewhere now. Don't reintroduce them.

## Build System

The source lives in `src/` as ES modules and is bundled by esbuild into the single userscript file users install: `nuke-family-helper.user.js` at the repo root. **Never edit `nuke-family-helper.user.js` directly** — edit `src/` and rebuild. CI (`.github/workflows/verify-build.yml`) fails if the committed file doesn't match a fresh production build.

```bash
npm install          # once
npm run build        # production build (ALWAYS run before committing)
npm run watch        # rebuild on save (production settings)
npm run watch:debug  # rebuild on save with debug on (nuke.test API + console logging)
```

- The userscript metadata header is generated from `src/header.txt`; the `@version` comes from `version` in `package.json` (single source of truth).
- `__DEBUG__` and `__VERSION__` are compile-time defines injected by `build.mjs` (see `src/core/config.js`).
- Debug builds point at `http://nuke.test/api`. There is no hardcoded dev token; press Connect against nuke.test, or set one via its token-generation page or `GM_setValue("apiToken", "...")` from the userscript manager console.

## Development Workflow

For local testing, install `dev.user.js` in your userscript manager. It loads the built file from disk via `@require file://...`, so run `npm run watch` and reload the Torn page after each change. `dev.user.js` also matches `http://nuke.test/auth/token-generation` for testing the token flow against a local nuke.family instance.

Before releasing: run through `TESTING.md`, bump `version` in `package.json`, `npm run build`, commit `src/` and the regenerated `nuke-family-helper.user.js` together. Users install from the raw GitHub URL of the root file and the in-script update checker scrapes `@version` from it, so the built file must stay committed at that exact path.

## Automated UI tests

`npm test` runs Playwright (headless Chromium) against sanitized captures of real Torn pages (profile, faction tabs, hospital) styled with Torn's real CSS, in both light and dark mode, with `GM_*` and the nuke.family API stubbed. Setup once: `npx playwright install chromium`. Torn's CSS is committed in `test/fixtures/torn-css/`; `npm run fixtures:css` fetches stylesheets newly referenced by a fixture, `npm run fixtures:css:refresh` re-downloads everything on request. Screenshots land in `test/screenshots/` (gitignored); read them to check how new UI looks. When adding or changing UI, add/extend a test in `test/features/`, loop over `THEMES`, and add any new API route to `test/fixtures/api/default.json`. Never commit raw captures: new pages go through `npm run fixtures:sanitize` (see `test/README.md`). Fixtures are snapshots, so this does not replace the real-site pass in `TESTING.md`.

## Code Architecture

### Entry point and feature dispatch

`src/main.js` bootstraps the script. On the nuke.family token-generation page it only runs token capture and returns (the Torn-side bootstrap, including the first-run token prompt, must never run there). On Torn: PDA polyfill first, then (in TornPDA only, the one asynchronous step) the app's store, then styles, update check, cached-data load, the key and the connection bar, and finally feature dispatch. A **feature** is a module exporting `{ name, pages: [PageType], init() }`. `dispatchFeatures()` runs `init()` for every feature whose page matches the current URL, both on load and on SPA navigation (`onNavigate` in `src/core/pages.js` hooks hashchange/popstate/pushState plus a deduped poll — Torn's faction page switches tabs via the location hash).

`init()` must be idempotent, and **must guard on DOM presence, not a module-level boolean**. Torn rebuilds whole tab panels when you navigate away and back, so a "already injected" flag stays set while the injected elements are gone — this was a real bug where faction-page buttons disappeared until a full reload. For containers the page may rebuild asynchronously, use `ensureInjected()` from `core/dom.js`, which re-checks on a short bounded schedule and repairs a wiped injection.

**To add a new feature:** create a module in `src/features/` exporting the descriptor, register it in the `features` array in `main.js`, and add a `@match` line in `src/header.txt` if it targets a URL not already matched.

### Core modules (`src/core/`)

- `pda-polyfill.js` — GM_* API polyfill for the TornPDA mobile app; must be imported first. Exports `isPda`, which goes by the user agent (`com.manuito.tornpda`): the app's built-in GM layer calls itself "GMforPDA version 2.2", so the script handler name alone does not say.
- `config.js` — build-time constants: `DEBUG`, version, `API_URL`, GitHub update URL.
- `api.js` — `api(path, {method, data})`: promise-based, authenticated JSON calls to the nuke.family API via `GM_xmlhttpRequest`; throws `ApiError` with `.status`/`.body` on non-2xx (and `.raw`, the start of a body that was not JSON), or `NoAnswerError` with a `.kind` (`network`, `timeout`, `empty`, `not_json`) when nothing usable came back. `request()` is the low-level wrapper. Every `api()` call sends `X-NFH-Version`, `X-NFH-Client` (`browser`/`TornPDA`) and `X-NFH-Manager`, plus `X-NFH-Failures` (calls that got no answer since the last one that did, kept in localStorage `nfhUnansweredCalls`) when there were any; nuke.family counts these per feature for Super Admins at `/admin/script`. A call that is not a feature's own use passes `feature` (`X-NFH-Feature`: the debug report's probes send `debug-info`, the by-hand key check `connect`), and `labelRequests(label, work)` labels every call made while `work` runs (Check NFH Updates uses `check-updates`). Header values must be strings: TornPDA hands them to Dart as `Map<String, String>`. `pageRequest()` sends none of these (a custom header would make the page's `fetch()` preflight). The script must not track anything beyond these headers on calls it already makes. `token` sends a key other than the stored one (`""` for none); only calls made with the stored key count towards the connection state. `publicApi()` is for the routes that need no key: the userscript manager first, the page if that gets no answer. `pageRequest()` makes the same call from the page with `fetch()`, never with the key, for the routes that need none: the userscript manager's requests can fail on their own (seen on TornPDA).
- `storage.js` — where the key and the member's settings are kept (`getValue`/`setValue` for the userscript manager's values, `getItem`/`setItem` for settings, with localStorage's string-or-null shape). In a browser that is GM storage and localStorage, unchanged. In TornPDA, whose "GM" storage is really the page's evictable localStorage, the app's own per-script store (`PDA_storage`, async, SQLite) is the source of truth when it exists: `initStorage()` loads it once into memory before `main.js` starts anything, copies across whatever only the old place has (the migration, nothing for the member to do), restores to the old place what only the app has, and every write goes to both. A write the app did not confirm is listed in `nfhNativeStorageUnsaved` so the old place's newer value wins on the next load. Keys are listed at the top of the file: **a new setting that should survive a cache clear must be added there and read through this module**. Re-fetchable caches stay in localStorage on purpose.
- `auth.js` — holds the API token (through `storage.js`) and knows whether it is working: `connectionState()` is `connected`, `missing` (no key), `rejected` (nuke.family answered a call made with the stored key with 401) or `unreachable` (calls are getting no answer and none has got through), fed by `api()` and announced through `onConnectionChange()`. How a key is obtained is `features/connect.js`.
- `synced-store.js` + `cache-sync.js` — localStorage-backed stores (shitlist, categories, contracts) refreshed via the server's `/cache/last-updates` timestamps, with per-store TTL fallback. Store keys match the pre-refactor layout so existing installs keep their cache, except contracts, which moved to `contractCoverage` when it switched to `/contracts/active-coverage`. `refreshAllCaches()` force-refetches every store plus role and permissions (used by the "Check NFH Updates" button as a stale-data escape hatch); stores are registered in `main.js` before any feature runs so it always covers all of them.
- `pages.js` — `PageType` enum, URL matching (`IsPage`), navigation events (`onNavigate`).
- `torn-page.js` — scraping helpers for Torn's DOM (viewed player/faction, logged-in user via `uid` cookie).
- `settings.js` — user preferences (category visibility, reputation box) in localStorage.
- `user.js` — nuke.family role + permissions (12h cache) for gating UI, with `refreshUserRole()` / `refreshPermissions()` for forced refetches. The role call also says whether the member is in a reviving faction: `inRevivingFaction()` returns true, false or null (not known yet), refetches the role in the background once per page when that answer is missing or over 12 hours old (only with a key stored), and `onUserRoleRefreshed()` tells listeners when it arrives.
- `update-checker.js` — GitHub version check with 6h throttle and 3-day nag grace period.
- `dom.js` — `waitForElm`, `addStyle`, `escapeHtml`. **All API/user-sourced strings interpolated into innerHTML must go through `escapeHtml`.**

### Features (`src/features/`)

- `shitlist/` — data stores (`data.js`), profile section (`profile.js`), unified entry renderer (`render.js`), submission form + warning dialog (`form.js`), settings panel (`settings-panel.js`).
- `contracts.js` — the profile "Active Contract" box is a setting in the cog panel (`SettingsManager.isActiveContractVisible()`): always on and locked, with the reason on hover and in a note, for a member of a reviving faction; off by default for anyone else, who can turn it on (`nfhShowActiveContract`); shown while the faction is not known yet. `applyActiveContractSetting()` adds or removes the box after the setting or the member's faction changes, and tells `onActiveContractSettingChanged()` listeners (the hospital rows recolour). The setting covers the hospital contract colours too, and while it is off the coverage store is not fetched at all (a synced store's `enabled` option); it is fetched again, being stale by then, when the setting comes back on. Coverage store (`/contracts/active-coverage`: each entry has an optional `faction_id` and optional `player_ids`, so player or group contracts need no script change), active-contract matching (UTC date parsing), profile "Active Contract" section (lists every rule when a contract has several).
- `hospital.js` — hospital row colour-coding (contract > friendly > shitlist). Contract colours only while the Active Contract setting is on.
- `reputation.js` / `recruiting.js` — profile reputation box and permission-gated ML recruiting score. The box is a cog-panel setting (`SettingsManager.isReputationVisible()`): locked on, with the reason on hover and in a note, for a member with `recruiting.predict` (the "Check Recruiting Score" button lives in the box; decided from the cached permissions, fetched before hiding the box); otherwise the member's own choice (`nfhShowReputation`), defaulting to on unless their faction is known not to revive. `applyReputationSetting()` re-applies it when the role or permissions are fetched again.
- `chain-watch/` — bar under the chain box on your own faction's main tab, driven by the nuke.family chain watch API (`/chain-watch…`): slot signup, self check-in/out, the slot-end "still watching?" answer, and staff check-in/out of other members (gated by `can_manage_attendance` from the board payload, not the cached role). Also the chain timer alert (flash + beep) that replaces the old standalone "Chain watcher" script, importing its `chainWarcher` settings. `data.js` API + caches, `view.js` pure HTML rendering, `alert.js` timer alert, `prefs.js` settings, `index.js` controller. This page is busiest during wars, so keep it cheap: the watch list is cached 10 min (most page loads make no request), polling only runs while the tab is visible, and regions are only rewritten when their HTML changed.
- `retals/` — retal alerts (plan: `docs/retal-alerts-plan.md` in the site's repository; steps 1-3 built, notifications, settings and stat estimate tags still to come). On your own faction's main tab (`isOwnFactionMainTab()` in `core/torn-page.js`, shared with chain watch), `capture.js` hears Torn's chain feed without ever asking Torn for anything: a script tag runs in the page (a userscript's own window may be a sandbox) and wraps the page's XMLHttpRequest and fetch for `faction_wars.php?step=getwardata&wardescid=chain`, and also reads `warDesc.recentAttacks` from the React props behind `.chain-attacks-list.recent-attacks` every 2s (which catches the first load, made before the script runs, and fires again whenever Torn draws the list anew). It hands the attacks back as a JSON string in a `nfh:chain-feed` DOM event. `logic.js` (pure, unit tested) maps Torn's fields to the site's and keeps only what the site acts on: an enemy hit on one of ours, not stealthed, that took respect, or our hit carrying Torn's `retal` flag, within 5 minutes. `data.js` sends those to `POST /retals/report`, remembers attack ids already dealt with (localStorage `nfhRetalsSent`), and calls `GET /retals` and `POST /retals/{enemyId}/claim|unclaim`; every answer is `{ server_now, retals }` (refusals included), and `server_now` sets the countdown clock. `view.js` renders the list (`#nfh-retals`, chain watch bar styles plus `nfh-rt-*`) right after Torn's recent attacks, hidden when nothing is open: enemy linked to their profile with faction tag, who they hit, a countdown, Claim/Unclaim, Attack, "Claimed by X", and done retals greyed out for two minutes. Attack claims first and then opens the attack page (a new tab, opened inside the click, in a browser; the same view in TornPDA); someone else's live claim, or a 409 from the claim, gets a warning with "Attack anyway" and closes the opened tab. `index.js` is one 1s timer that only exists while the recent attacks list is on the page: it redraws only when the HTML changed, re-mounts after React re-renders, and polls `GET /retals` every 10s while the tab is visible and no other answer came in that time. A 403 (not in a Nuke faction) or a 404 without a list (a site without retals) stops everything for that page. `[retals]` `LogInfo` lines record which way the feed arrived and a stealthed attack as Torn gives it.
- `ranked-war/` — war board on a ranked war view (`#/war/rank`): your own faction's (`step=your`) or any other faction's from its page (`step=profile&ID=…`, sent to the site as `faction_id`; `viewedWar()` tells them apart and `watch()` drops one war's state before showing another's). Driven by `/war/board` on nuke.family, which knows whether the faction is at war (its own factions from its ranked war sync, any other by asking Torn, cached five minutes), reads both factions' member statuses from Torn once for everyone looking, and holds the battle stat estimates members' scripts pass on. The script never calls Torn's API. Stat estimates are BSP's or FF Scouter's, never ours: a member running either has them on the row already (BSP's `.iconStats` box beside the name, exact figure in its `data-bsp-stats`; FF Scouter's `data-est-value` on the row; both confirmed on live Torn), so they are read from there, used for the stat sort, and sent to `POST /war/estimates` when the site has none from the last day for that player and source (one request per source, a few seconds after the list settles). Members running neither get the site's copy as a small badge. `pickEstimate()` decides which to use: the page before the site, the preferred source (a bar setting) before the other. A list FF Scouter is filtering (`data-ffscouter-active-filter`) is not re-sorted. Status cells get a hospital countdown or travel label drawn over Torn's own text from a `data-nfh-war` attribute (Torn keeps rewriting the text, so it is never edited), and each list is kept sorted by status or by stat estimate (`prefs.js`, this browser only). With the status sort, a "then" select picks how members with the same status are ordered (`Then` in `logic.js`: stats either way, the war score Torn shows in the row either way, or latest out of hospital); it orders the okay group and breaks ties in the others. `logic.js` holds the pure rules (unit tested): Torn's live cell beats the few-seconds-old API where they disagree. `index.js` is one 1s timer that only exists while that view is open, polls only while the tab is visible, writes an attribute only when it changed and moves rows only when the order is wrong. Cells are found by plain or build-hashed class (`status` / `status___…`). The bar reuses the chain watch bar's styles.
- `organized-crimes/` — OC Assistant on your own faction's crimes page, driven by the faction's config from nuke.family (`/oc/config`, a synced store keyed on `oc_config_cache_last_update`). Every slot gets a "Min CPR" line; on the Recruiting sub-tab the best slot to join is tagged and named in a bar above the list. A crime too new for the site to have weights (or any entry at all) is still suggested, on the level's fallback minimum and the member's CPR, ranked after an equal crime whose weights are known. `remote.js` sends the viewer's own CPRs (read from open slots, only when one changed) to `/oc/cpr` and caches the faction's board (`/oc/board`, one minute) so a better slot in a crime Torn has not lazy-loaded yet can be named in the bar. Staff (whoever the board sends `members` to; the site decides, not the cached role) get flags under filled slots on Recruiting and Planning: unqualified, not productive, under-levelled, each with its own colour and symbol, toggled and given personal thresholds in the bar's "Flag settings" (`prefs.js`, this browser only). A member already in a crime is recognised by finding their own player id in a filled slot (on the page first; the board only for crimes not on the page), never by the Join buttons, which Torn leaves live: they get no suggestions and no crime request, just a line naming their crime and role. A member sitting in a slot that would be flagged, in a crime with more than 24 hours left, is warned in the bar and shown better slots; that warning always uses the faction's thresholds. `flags.js` holds the pure flag rules (unit tested). The faction chooses on nuke.family how much of this its members get (`memberFeatures()` in `scoring.js`; a switch an older site does not send counts as on): the whole assistant, slot suggestions, the own-slot warning, and whether roles show the minimum CPR (only hideable when nothing is suggested or warned about). Role weights are separate and do not depend on the minimums: `weightsChoice()` uses the faction's `show_role_weights` (off for every faction to start, and off on a site that does not send it) until the member ticks or unticks "Show role weights" under the bar's Settings, which is saved with the faction's id (`nfhOcWeights`, `prefs.js`) and dropped when they are seen in another faction. With both on a role reads "Min CPR 63 · 13.5%", with only weights "Weight 13.5%". The bar always shows while crimes are on the page, at least "OC Assistant" and its Settings button (role weights for everyone, plus the flag settings for staff). Staff flags are never among these, since each staff member toggles them personally, and CPRs are uploaded regardless. The faction also sets the crime level productive days count from (`productive_from_level`, null for never): below it no wait is "not productive" for suggestions, warnings or staff flags, and equal crimes are ranked closest to full first rather than shortest wait. Suggestions also respect the viewer's own level (from the board): `belowOwnLevel()` holds a member whose level is one productive days count at to that level exactly (any lower crime), and anyone else to the faction's under-level gap. Such a crime is never "Good for you": at most one is tagged, "Best available" with a "Below your level" line, the bar says so in red, and it does not count as a decent slot, so the crime request is still offered. One below by the under-level gap or more is not shown at all to a member who can ask staff for a crime. Level 9 and 10 crimes cannot be spawned directly (they are later stages of a chain that starts lower), so every one of these rules, and the staff under-levelled flag, judges a level 9 or 10 member as level 8 (`heldLevel()`, `HIGHEST_SPAWNABLE_LEVEL`): a level 8 crime is not below their level, though it is only tagged when no level 9 or 10 crime suits them, and the crime request is for "7-8", never "9-10" (the site's `tierFor` agrees). When the faction allows it and the member is at or above its minimum level, a member free to join with nothing decent open at their level gets an "Ask staff for a level N crime" button (`POST /oc/spawn-request`; the site enforces the rules and a cooldown, and fog-bot posts it in Discord). `data.js` config store, `catalog.js` name-key lookups, `page.js` reads Torn's DOM (class names matched by prefix, planning progress from the slot clock's conic gradient), `scoring.js` pure rating and ranking (unit tested in `test/unit/`, so it must not import anything that needs the browser or build defines), `view.js` idempotent DOM upserts, `index.js` controller with a debounced MutationObserver on `#faction-crimes-root` (Torn lazy-loads and re-renders the list; mutations made only of our own elements are ignored). The full plan, including the steps not built yet, is `docs/oc-assistant-plan.md` in the site's repository.
- `connect.js` — connecting the script to the member's nuke.family account, and saying so whenever it is not connected. Not a registered feature: `main.js` calls `initConnect()` on every Torn page. **Nothing may ask for a key in a dialog on page load** (the old `confirm`/`prompt` first-run flow is gone). Instead a bar at the top of the page (`#nfh-connect-banner`, hideable for a day) says the script is not connected, was disconnected, or cannot reach nuke.family, and a one-line note is put beside each feature's area (`NOTE_HOSTS`, found by selector so features need no change). Connect is a pairing, with no key typed or copied: `POST /script/connect` hands the script a secret and a page address; the member approves on that page (logged in, or with just their Torn API key, which only the site ever sees and which makes a script-only account); the script polls `POST /script/connect/token` with the secret every few seconds while the tab is visible until it is handed its token, then reloads. The pending secret is kept through `storage.js` so a member who comes back to a fresh page (TornPDA opens nuke.family in the same view) is picked up again. In a browser the tab is opened inside the click and pointed at the address afterwards (popup blockers); in TornPDA the banner's own link is tapped. `enterKeyByHand()` is the fallback: it turns away a 16 character Torn key with an explanation and checks any other key with the site before keeping it.
- `faction-buttons.js` — "Change Nuke Family Key" (the by-hand fallback above), "Check NFH Updates" (which also force-refreshes all caches) and "NFH Debug Info" on the faction controls page. This is the only settings surface outside the profile-page cog.
- `debug-info.js` — the report behind the "NFH Debug Info" button on the faction controls page: script version and manager, whether the key is accepted, and for role, permissions, cache timestamps, OC config and OC board both what nuke.family answers right now (status and the site's reason on a refusal) and what is cached. Each failed request says how it failed (no reply, timeout, or a reply that is not the API's, with its first characters), and `site_from_page` says whether the page itself could reach nuke.family, which separates the userscript manager's requests failing from the device being unable to reach the site. Shown as JSON in a dialog with a Copy button, and (being too long for a Discord message) a "Send to developer" button that posts it to `/script/debug-report` on nuke.family, which needs no key (sent by the page instead when the userscript manager's request gets no answer, marked `sent_by: "page"`), and shows the six character reference the site hands back; Super Admins read the reports at `/admin/script-debug-reports`. It must never include the key or other members' data (stored entries are reported by size and count only).
- `token-capture.js` — the older way of connecting, kept working for anyone who uses that page: captures the API token on the nuke.family token-generation page and sends the user back to Torn if a return address was stored. The script no longer sends anyone there. Not a registered feature; `main.js` calls `initTokenCapture()` directly.

### Conventions

- All injected elements use the `nfh-` CSS class prefix; styles live in `src/styles.css` (theme-aware via CSS variables).
- `LogInfo()` (in `core/log.js`) for debug logging — it's a no-op in production builds; don't use bare `console.log` except for real errors.
- localStorage keys are shared with the game's origin; GM storage (`GM_getValue`/`GM_setValue`) holds the API token.
